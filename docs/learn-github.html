01 — Mental model

Git stores your work as a chain of commits. Each commit is an immutable snapshot of your project at a moment in time, with a parent pointer to the previous commit. The chain is a tree (or graph, when branches merge back).

A branch is just a moveable label that points at a commit. Switching branches moves your working directory back to whatever the branch's commit captured. Creating a branch is cheap — it's a single new label.

HEAD is a label that points at "where you are right now." Usually it points at a branch (which points at a commit). When you commit, HEAD's branch label moves forward with you.

Time flows left to right. Each dot is a commit. The coral pill is your current branch + HEAD.

When you make changes and commit, a new commit appears on the right, and the branch label (with HEAD) moves forward to it. When you branch, you add a second label pointing at the same commit, then commits diverge into two lines.

Why this matters

Once you internalize "branch = label, commits = immutable nodes", git stops feeling magical. Every git command is moving labels or adding nodes.

02 — The daily loop

Four states a change can be in, and the commands that move it between them:

The four-stage flow. Only commits in "local repo" are durable. Files in working tree can be lost on branch swap.

The commands

$ git status # what's changed? $ git add <file> # stage a specific file $ git add . # stage everything (careful) $ git commit -m "fix login" # snapshot the staged changes $ git push # upload commits to GitHub $ git pull # download other people's commits
Commit early, commit often

A commit makes your work durable. Files that exist only in the working tree can vanish if you switch branches, and they aren't on GitHub yet. Every meaningful chunk of progress deserves its own commit. Five small commits beat one giant commit you can't easily review or revert.

Don't bypass safety with --force or --no-verify

git push --force can erase other people's work from the remote. git commit --no-verify skips pre-commit checks (in Pulse, that's the gitleaks secret scan). If a hook is blocking you, fix the underlying issue. The hook is there because somebody learned the hard way.

03 — Branches: the safety primitive

A branch is just a moveable label. Creating one is essentially free, and it's the most important habit you can build. One task = one branch. Never edit directly on main.

When you branch, you're saying "I'm about to try something — if it goes well, I'll merge it back into main; if it goes badly, I'll throw the branch away and main is untouched."

A feature branch's life cycle. Branched at a3, two commits on the branch, merged back via PR to become a4.

Branching commands

$ git checkout -b feat/my-task # create + switch to new branch $ git branch --show-current # where am I? $ git branch # list all local branches $ git checkout main # switch to main (only if working tree clean!) $ git branch -d feat/old-task # delete merged branch (safe)

04 — The PR cycle

A Pull Request is GitHub's way of saying "I want to take these commits from my branch and put them on main, please review first." This is how all code on Pulse's main branch gets there.

The seven steps of every PR. Steps 1-3 happen locally; 4-7 use the gh CLI.

The full walkthrough

  1. Branch off latest main.
    $ git checkout main $ git pull $ git checkout -b feat/my-task
    Or in Pulse: /task-start feat/my-task — does all three for you.
  2. Make changes. Commit them. Often. Small commits.
    $ git status # see what changed $ git add <files> # stage specific files $ git commit -m "feat(messages): add voice attach"
  3. Push the branch to GitHub.
    $ git push -u origin feat/my-task
    The -u sets the upstream so future git push doesn't need arguments.
  4. Open the PR from the terminal.
    $ gh pr create --base main --head feat/my-task --fill https://github.com/FatherSonOne/Pulse-1/pull/76
    --fill auto-uses your commit messages as the PR title + body. For a richer description, drop the flag and write one.
  5. Review. Self-review your own diff in the PR view, OR have another person look. Add comments inline. Push more commits to address feedback.
    $ gh pr view 76 # open PR in browser $ gh pr diff 76 # see the full diff $ gh pr checks 76 # CI status
  6. Merge when ready.
    $ gh pr merge 76 --merge --delete-branch ✓ Merged · branch deleted on remote · switched to main + pulled
    --merge = preserve commit history with a merge commit. --delete-branch cleans up both remote and local branches automatically.
  7. You're back on main, up to date. Start the next task.
    $ /task-start feat/next-task
Merge strategies

--merge preserves the full commit history with a merge commit (clearest audit trail). --squash collapses all PR commits into one (cleanest history). --rebase replays each commit onto main linearly (no merge commit). For Pulse, --merge is the default — you can see exactly what landed and when. Use --squash for PRs with a lot of work-in-progress noise commits.

05 — Pulse's slash commands

Two commands wrap the entire above flow into one keystroke each.

/task-start

Begin a new task

Sanity-checks your tree, switches to main, pulls, validates the slug, creates the branch, prints the policy reminder.

/task-start feat/voice-messages /task-start fix/login-redirect /task-start refactor/x --worktree
/git-commit

Commit + push

Runs a secret scan, checks .gitignore coverage, stages, commits with a descriptive message, pushes to the current branch.

/git-commit
Mental shortcut for the whole cycle

/task-start feat/x → edit code → /git-commit → gh pr create --fill → gh pr merge <num> --merge --delete-branch. That's it. The four-step Pulse loop.

06 — Parallel work (when you need it)

By default in Pulse, one Claude session at a time per working tree. This was locked in CLAUDE.md § 1 after three lost-work incidents in May 2026, all caused by two sessions both calling git checkout in f:/pulse1/.

When you genuinely need two surfaces worked at once, use worktrees. A worktree is a sibling directory linked to the same repo but on a different branch. Two physical directories means zero collision.

Two worktrees share one .git/. They share commits via push/fetch, never through working-tree state.

Spawning a worktree

PS> .\scripts\branch-safety\new-worktree.ps1 -Slug other-task Creating worktree: branch: feat/other-task (off main) directory: ..\pulse1-other-task Done. To start a parallel Claude session there: cd '..\pulse1-other-task' # then open a new Claude Code window pointed at this directory

Then open a new Claude Code window, pointed at the new directory. That window is a separate session — it can checkout, commit, push freely without ever touching your main window's working tree.

Cleaning up when you're done

$ cd f:\pulse1 # back to your main session $ git fetch # pull the other tree's branch ref $ git merge origin/feat/other-task # bring the work onto main locally $ git worktree remove ..\pulse1-other-task # tear down $ git branch -d feat/other-task # delete the local branch (now merged)
The rule that prevented the May 2026 incidents

Never run two Claude sessions in the same f:/pulse1/ directory. One window per directory. Two directories for two windows. The post-checkout banner in .git/hooks/ will warn you loudly if a branch swap happens — pay attention to it.

07 — Recovery (when things go wrong)

Almost nothing in git is permanently lost. Commits live forever (until garbage collection, which takes weeks); branches are just labels you can recreate; even "deleted" branches stay around in the reflog. Always diagnose before recovering.

Recovery checklist

  1. Where am I?
    $ git branch --show-current
  2. What's the working tree state?
    $ git status --short
    Note any untracked files (??) — those are only in the working tree, never in any commit, and they vanish if you switch branches.
  3. What happened recently?
    $ git reflog --oneline -30
    Every checkout, commit, merge, and reset is recorded here. If a branch swap dropped your work, the reflog shows checkout: moving from X to Y — recover by checking out X again.
  4. Where does a missing file live?
    $ git log --all --oneline -- src/path/to/file.tsx
    Searches every branch's history for that file.
  5. What branches exist?
    $ git branch -a # local + remote $ git worktree list # if work is in a sibling worktree

Common situations

Situation

"My uncommitted work disappeared after switching branches"

Cause: untracked files don't survive branch swaps.

Recovery:

$ git reflog $ git checkout <previous-branch>
Then commit immediately. Prevention: commit before you switch branches. Always.
Situation

"I committed to the wrong branch"

Cause: you forgot to git checkout -b before working.

Recovery:

$ git checkout -b feat/my-task # claim the new commits $ git checkout main $ git reset --hard origin/main # reset main
Situation

"git pull complained about conflicts"

Cause: remote and local diverged.

Recovery: Open the conflicted files. You'll see <<<<< / ===== / >>>>> markers. Pick which side you want (or both), delete the markers, save. Then:

$ git add <file> $ git commit # merge commit message ready
Situation

"I accidentally committed a secret"

Cause: didn't see gitleaks warning, or bypassed it.

Recovery: If not yet pushed, git reset HEAD~1 + scrub the secret + recommit. If already pushed, rotate the secret first, then talk to the team about a history rewrite. Don't try to delete-and-force-push without coordination.

Before any destructive command

Anything ending in --force, --hard, or -f can lose work. git reset --hard, git checkout --, git clean -f, git push --force. Stop and diagnose first. Ask yourself: "If I'm wrong about what this command does, what's the worst case?"

08 — Working with Git in your IDE (Cursor / VS Code)

Everything in this guide works from the terminal. But your IDE has a built-in view of the same information, and once you can read it, you'll catch problems before they become incidents. Cursor and VS Code share the same Source Control panel — the keyboard shortcut and the UI are identical.

Opening Source Control

Ctrl+Shift+G on Windows / Cmd+Shift+G on Mac, or click the branch icon in the activity bar (the third or fourth icon down on the left edge).

The Source Control panel. Status letters: M = modified, U = untracked, A = added/staged, D = deleted.

Reading file status

Each file gets a single-letter badge on the right that tells you what state it's in:

BadgeMeansWhat to know
MModifiedTracked file you've edited. Staged or unstaged depending on which section it's in.
UUntrackedNot in any commit yet. If you switch branches, it'll likely vanish. Commit or stash before swapping.
AAdded (staged)New file, staged for the next commit.
DDeletedFile removed. Stage it to record the deletion.
CConflictMerge conflict — needs resolution. The file has <<<<< markers inside.
RRenamedTracked file renamed.

Staging + committing from the IDE

  1. Hover any file under "Changes". A + button appears to its right. Click to stage just that file. The file moves up into "Staged Changes".
  2. Click the file name to see the diff in the main editor. Green is added, red is removed. Read it before committing.
  3. Type a commit message in the message box at the top of the panel. Use Pulse's conventional-commits style: feat(messages): add quick replies, fix(login): handle empty password.
  4. Click "Commit" (or Ctrl+Enter with the message box focused). Only staged changes go in.
  5. Sync — there's a small sync icon (circular arrows) in the bottom-left status bar. Click it to push your commit + pull anything new. Or use the terminal: git push.
The "Stage All Changes" shortcut

The + next to the "Changes" section header stages everything in one click. Convenient, but it's how secrets get committed — you stage a .env file you didn't notice was modified. Prefer staging files individually until you've built the habit of reading the file list first.

The native Graph view (built-in)

At the bottom of the Source Control panel is a "GRAPH" section showing recent commits as a tree. Each row is one commit, colored lines show how branches diverged and merged. Cursor / VS Code show the current branch's tip with a colored ring; merge commits show two parent lines.

Hover any commit to see its message and author. Right-click → "Copy commit hash" to paste anywhere, or "Show in editor" to open the diff. The native graph is fine for a quick "what merged recently?" glance, but for anything richer, install Git Graph.

Git Graph extension (highly recommended)

The Git Graph extension by mhutchie is the most-installed Git extension on the marketplace for a reason. It replaces "look at a flat list of commits" with a full interactive graph of every branch, every merge, every tag, every stash, with click-through context menus for almost every git operation. Install:

$ code --install-extension mhutchie.git-graph # VS Code $ cursor --install-extension mhutchie.git-graph # Cursor (same extension)

Or marketplace search: "Git Graph" by mhutchie. Free, no account, no telemetry.

Git Graph view. Each branch is a colored vertical line. Merges show as branch lines reconnecting to the main trunk. Branch + tag refs are pills next to the commit they point at.

What Git Graph unlocks (right-click anywhere)

The two most useful Git Graph workflows

  1. "What did I just merge?" Open Git Graph → look at the colored merge lines coming into main. The branch each merge came from is visible as a pill. Click the merge commit → see the full diff. 5 seconds.
  2. "Where is that lost commit?" Open Git Graph → toggle "Show: Remote Branches + Stashes + Tags" in the top-right options. Every commit that exists anywhere in the repo, including detached / orphaned ones, will appear. Find it, right-click → "Create branch from here" → recover.
Git Graph as a checkout-safety check

Before you switch branches in the terminal or status bar, glance at Git Graph. If your current branch has commits that aren't reachable from where you're about to land, those commits are about to fall off your working tree. Recovery is straightforward (the commits stay in git's reflog), but it's better to see the issue before it happens.

Switching branches via the status bar

The bottom-left corner of the IDE shows your current branch name (e.g. main or feat/quick-replies). Click it — a dropdown lets you switch to any branch.

The branch picker IS a git checkout

Clicking a different branch in the status bar runs git checkout <branch> under the hood. Same risks: untracked files can disappear, the post-checkout hook fires. Always check the "Changes" section first. If you see anything with a U badge, commit or stash before switching.

Resolving merge conflicts

When git pull or git merge hits a conflict, files with conflicts get the C badge. Click the file to open it. The IDE inlines colored bands around each conflict, with "Accept Current Change", "Accept Incoming Change", "Accept Both", and "Compare Changes" buttons above each conflict block.

Pick the resolution (or hand-edit to combine), then save. The badge changes from C back to M. Stage the file, commit, done.

GitHub integration (the GitHub Pull Requests extension)

Install the GitHub Pull Requests and Issues extension (made by GitHub, free, both Cursor + VS Code). Once signed in via gh auth login in the terminal or the extension's prompt, you get:

  • A "GitHub Pull Requests" panel listing open + assigned + draft PRs across the repo
  • Inline PR comments rendered directly in the diff editor
  • "Create Pull Request" command (palette: Ctrl+Shift+P → "Create PR") — UI equivalent of gh pr create --fill
  • Status checks for the current branch's PR (CI passes / fails) visible in the status bar
  • "Checkout PR" — pulls down someone else's PR branch for local review

Cursor-specific: AGENT REVIEW

Cursor's Source Control panel shows an "AGENT REVIEW" section with a "Find Issues" button. It runs the Cursor AI agent against your staged + unstaged changes before you commit, looking for likely bugs, missed edge cases, or accidentally-committed secrets. Worth running on any non-trivial commit. Treat its output as a second pair of eyes, not as gospel — it can hallucinate.

Best practices for IDE-based Git work

Do
  • Open Source Control (Ctrl+Shift+G) before any commit. Read the file list.
  • Click each file in the diff before staging — make sure it's what you think it is.
  • Use the terminal for any git checkout to another branch. The visual feedback is better there.
  • Watch for U badges before switching branches.
  • Use AGENT REVIEW (Cursor) before committing non-trivial diffs.
  • Keep the GRAPH section visible — it's your "where am I, what just happened" radar.
Don't
  • Click "Stage All Changes" reflexively. Secrets and stray edits hide there.
  • Use the IDE's "Sync" button for the first push of a branch. Use the terminal: git push -u origin <branch>.
  • Trust the status bar's branch indicator to tell you it's safe to swap. Check git status first.
  • Commit from the IDE without reading the diff. The diff editor is right there.
  • Have two IDE windows open on the same repo directory. Pick one. (Same rule as parallel Claude sessions — use worktrees.)
The .env file trap (visible in the source control panel)

If you see .env, .env.local, .env.production, or anything ending in .key / .pem showing up as A or M in your changes list — stop and check the gitignore. Those files should never be staged. The gitleaks pre-commit hook will catch most secrets, but it's safer to never stage them in the first place. Right-click the file → "Add to .gitignore" if the IDE offers it; otherwise edit .gitignore directly.

The two-monitor habit

Put your code editor on one screen and a small terminal window on the other (or split-pane the IDE's integrated terminal). Use the IDE for diff-review + staging + commit-message + PR-comments, and the terminal for branch ops + recovery + gh. You'll catch about 90% of the mistakes this guide is designed to prevent.
